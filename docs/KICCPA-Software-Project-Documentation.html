KICCPA Website — Software Project Documentation

Production marketing site and in-house CMS for Kuwait International Company for Computer Programming Activities (KICCPA), strategic arm of KAM International. Documentation is derived from the repository at kiccpa-website (npm workspaces: frontend + backend).

Next.js 16.2.1 · React 19 Express 5 · MongoDB / Mongoose 9 NextAuth JWT Admin Live: kiccpa.com

1. Executive Summary and Synopsis

KICCPA is a monorepo web platform that markets enterprise digital solutions (LMS, SMS, AI counsellor, calendar, assessment, and related products) across GCC and India, captures leads and demo bookings, hosts downloadable resources, and provides a credentials-protected admin CMS for posts, testimonials, and resources.

Synopsis (as implemented)

  • Frontend: Next.js App Router app in frontend/ — marketing pages, forms, admin UI, API proxy, S3 video streaming, NextAuth.
  • Backend: Single Express process in backend/index.js — REST JSON API, Multer uploads, Nodemailer SMTP, Mongoose models.
  • Data: MongoDB Atlas (optional offline/mock mode when MONGODB_URI is missing).
  • Deploy targets (documented in repo): Amplify (amplify.yml), EC2+PM2 (deploy/), App Runner (backend/apprunner.yaml); production currently also runs on Render + Cloudflare DNS.

Primary public surface: homepage composed by frontend/src/frontend/lavender-home/LavenderHome.tsx. Brand identity uses navy/orange CSS variables in frontend/src/app/globals.css.

5. System Architecture

Request flow as implemented: the browser talks to Next.js. Most /api/* calls (except NextAuth and S3 video) are proxied by frontend/src/app/api/[...path]/route.ts to Express. Contact and demo server actions call Express directly via NEXT_PUBLIC_BACKEND_URL (frontend/src/lib/actions.ts).

10. Authentication and Authorization Flow

Authentication is implemented only on the frontend for the admin UI. Express endpoints are not protected by API keys or session middleware.

10.1 Sequence — admin login

sequenceDiagram participant U as User participant Login as Admin Login Page participant NA as NextAuth Handler participant Auth as auth-config.ts participant MW as middleware.ts participant CMS as Admin CMS U->>Login: Submit email and password Login->>NA: signIn credentials provider NA->>Auth: authorize credentials Auth->>Auth: timingSafeEqual check alt valid credentials Auth-->>NA: admin user object NA-->>Login: JWT session 8 hours Login->>CMS: redirect to CMS CMS->>MW: withAuth token check MW-->>CMS: allow access else invalid or missing env Auth-->>NA: null NA-->>Login: login error end

10.2 Implementation facts

  • Provider: Credentials (lib/auth-config.ts).
  • Compare via crypto.timingSafeEqual after UTF-8 buffers; length mismatch fails closed.
  • Session strategy: JWT; maxAge: 60 * 60 * 8.
  • Secret: NEXTAUTH_SECRET.
  • Middleware matcher: /admin, /admin/:path*; /admin/login allowed without token.
  • Sign-out: signOut({ callbackUrl: "/" }) from admin CMS.
Authorization gap: CMS write/delete/upload Express routes are publicly callable if the backend URL is reachable. Only the Next.js admin pages are gated. Hardening should add shared-secret or session verification on Express (see §20).

  1. Load dotenv.
  2. Ensure upload directory exists.
  3. Connect Mongo if URI valid; else warn and continue offline.
  4. Register routes.
  5. Listen on process.env.PORT || 5000 bound to 0.0.0.0 (Render injects PORT, often 10000).

14. Business Logic

14.1 Lead capture flow

flowchart TD A["Contact form"] --> B["Zod ContactSchema"] B -->|invalid| E["Return field error"] B -->|valid| C["POST api leads"] C --> D{"Mongo ready?"} D -->|yes| S["Save Lead"] D -->|no| L["Console log only"] S --> M["SMTP internal and user ack"] L --> M M --> R["201 success"]

14.2 Demo booking rules (backend/index.js)

  • Honeypot fields short-circuit with fake success.
  • Validate name, email regex, organization, country, product, goals length, time enum, date not in the past.
  • Generate DEMO-{base36}-{rand} reference.
  • Persist + notify LEADS_NOTIFY_TO (or default info@ addresses) + confirmation to user.
  • Duplicate key → HTTP 409.

14.3 School survey

  • Same honeypot pattern; reference prefix EDU-.
  • Normalize enums; truncate free-text; coerce arrays to strings.
  • Dual email (internal + user).

14.4 CMS content

  • Posts list returns only published: true when online; offline uses seeded mockPosts.
  • Get-by-slug does not re-check published flag.
  • Resources create requires live DB (503 otherwise).

20. Future Enhancements

Suggested improvements grounded in current gaps:

  1. Protect Express mutating routes — shared secret or JWT verification mirroring NextAuth.
  2. Restrict CORS to known frontend origins.
  3. Persist uploads to S3 instead of local disk (align with video pipeline).
  4. Automated tests + CI (GitHub Actions) for API and auth smoke checks.
  5. Remove unused deps (sanity, next-sanity, resend) or adopt them intentionally.
  6. Unify API access — route contact/demo through the Next proxy so only BACKEND_PROXY_URL is required.
  7. Admin update endpoints — today CMS is create/list/delete; no PATCH/PUT for posts/resources.
  8. Observability — structured logging, health that checks Mongo readyState, uptime alerts.
  9. Rate limiting on public POST endpoints (leads, demos, surveys, upload).
  10. Infrastructure-as-code — add render.yaml or Terraform for reproducible dual-service deploy.
